# Spike: OutLayer (Intel TDX) for Cynex evidence

Status: Final, SUPERSEDED. Two live requests made, both with no verifiable execution; see section 9. Verdict at the time: do not integrate (section 11). That verdict was later overturned: OutLayer IS integrated (see section 11 and the three-layer verification in docs/ledger.md), with live verified executions on requests 10640, 11912 and 13040 (test vault) and 13324 (production vault).

## What OutLayer is

OutLayer runs a caller-specified WASM module inside an Intel TDX confidential VM and returns the module's stdout to a NEAR contract through a yield/resume callback, with a TEE attestation for the run. The testnet contract is `outlayer.testnet`, mainnet `outlayer.near`. The contract source is fastnear/near-outlayer, read in full for this spike. The near-ai-cloud skill describes a different service (NEAR AI Cloud inference) and its verification flow is the model for the attestation section, not the OutLayer flow itself. The two are not conflated here.

## 1. The exact callback fields

`request_execution(source, resource_limits, input_data, secrets_ref, response_format, payer_account_id, params)` on `outlayer.testnet`. `resource_limits` is required even as `{}`: a request without it runs nothing (it becomes compile-only). The worker resolves with an `ExecutionResponse`:

- `success`: bool
- `output`: the guest's stdout, parsed per `response_format` (Text returns the raw string, Json returns the guest's JSON, Bytes returns raw bytes base64), or null when the run failed or produced nothing
- `error`: string, for example WASM hash mismatch or timeout
- `resources_used`: `instructions` (u64), `time_ms` (u64), `compile_time_ms` (Option<u64>, null when the WASM was cached)
- `compilation_note`: string, for example "Cached WASM from ..."
- `refund_usd`: stablecoin refund the guest chose to return

The calling contract receives the output through its own callback (the yield resume): the output as a JSON value for Json, a string for Text, base64 for Bytes, or null on failure. A failed execution is charged for the resources it used, capped at the compute deposit; a failure before the guest ran, or a promise failure, reports little or nothing and costs about the base fee (request 10262 was charged only the 0.001 NEAR base fee). The rest of the deposit is refunded automatically to the payer.

## 2. What is authenticated on-chain

Only one thing: the predecessor of `resolve_execution` must be the operator account, `worker.outlayer.testnet` (read live from `get_config`, owner `owner.outlayer.testnet`). The contract does NOT verify a TDX quote on-chain and does NOT verify a signature over the output in the generic flow. The attestation is produced off-chain and is verifiable by anyone afterwards (see section 3), but the chain never checks it.

How the operator account earns its keys is the part the chain does gate: a worker key is admitted to `worker.outlayer.testnet` only by `register_worker_key` on the register contract, which verifies the worker's TDX quote with dcap-qvl against Intel collateral, refuses any TCB status other than UpToDate and any quote with outstanding Intel advisories, requires all five measurements (MRTD + RTMR0-3) to match one owner-approved entry, and requires the submitted key to match the quote's `report_data`. That is the registration quote, a different quote from the per-execution one in section 3, whose `report_data[0..32]` carries the task hash, not a key. The key is then a function-call key scoped to `resolve_execution`, `submit_execution_output_and_resolve`, `resume_topup`, `resume_delete_payment_key`, with a 10 NEAR allowance.

Two honest limits, stated in OutLayer's own attestation doc: any access key on the operator account passes the session checks, so a full-access key on `worker.outlayer.testnet`, if one is present, would also be accepted; and the register contract's owner approves measurements and removes keys alone, without a vote.

So the on-chain trust statement is: the result came from a transaction signed by a key on the operator account, and that account's keys are gated by attested registration. The result bytes themselves carry no on-chain proof in the generic flow.

## 3. How the WASM hash binds to output

Three separate bindings, and they are not the same thing:

- The worker refuses a WASM file whose bytes do not match the hash. A project version is a file named by its sha256; a `WasmUrl` source carries the URL and the hash together.
- The per-execution TDX quote binds the task: `report_data[0..32]` is SHA-256 of the task fields in order, task_type, task_id, repo, commit, build_target, wasm_hash, input_hash, output_hash, block_height, caller_account_id, project_id, secrets_ref, timestamp, attached_usd. Absent optional fields are skipped; integers are little-endian.
- The quote is uploaded to the coordinator and fetchable at `GET https://testnet-api.outlayer.ai/attestations/{job_id}`, `/by-call/{call_id}`, `/by-request/{request_id}`, `/by-tx/{tx_hash}`. (api.outlayer.ai is the mainnet host; testnet uses testnet-api.outlayer.ai.) Verifying one means checking the quote's signature chain against the Intel collateral current when the execution ran (`GET /public/collateral?fmspc=&at=`), checking the five measurements against the register contract's approved list (`is_measurements_approved`), and recomputing the task hash from the inputs and outputs. The recomputed hash must then be compared against the quote's `report_data[0..32]`; that comparison, binding the independently checked request, WASM, input, and output values to the quote, is the step that establishes the binding. Without it the procedure proves nothing about which code ran or what it produced.

The attestation record schema, read live from an older execution (request 93): id, task_id, task_type, tdx_quote, worker_measurement, request_id, caller_account_id, transaction_hash, block_height, build_target, wasm_hash, input_hash, output_hash, timestamp.

## 4. Whether a separate signing key is involved

Yes, in the VRF flow, and no, in the generic flow.

- VRF: the worker builds an alpha from the request_id and sender_id (`vrf:{request_id}:{sender_id}:{user_seed}`), sends it to the Keystore TEE, and the Keystore signs it with an Ed25519 key that lives only inside the TEE, derived via MPC key ceremony. The output is SHA256(signature), and the signature is returned with the alpha and the value. Anyone can verify with `env::ed25519_verify` on-chain at about 1 TGas, or off-chain with the public key from `https://testnet-api.outlayer.ai/vrf/pubkey` (testnet key c0c5aeae1688c2f7cc2350aae1ee3ce96eddc0de84d678db873de48268f8cfa8; the mainnet host serves a different key). The VRF key is separate from the worker's key and from the calling contract.
- Generic flow: the worker's registered key signs the `resolve_execution` transaction with an ed25519 access key on the operator account. That authenticates the submitter of the transaction, not the output bytes. There is no separate signature over the output in the generic flow. The registration quote may carry an ml-dsa-65 key for attestation, but a NEAR transaction can only be signed by an ed25519 or secp256k1 access key, so ml-dsa-65 does not sign the transaction.

## 5. Measured cost, re-verified live

`estimate_execution_cost(resource_limits, input_len)` on `outlayer.testnet`, read live 2026-11-06:

- Defaults (null limits, null input): 7000100000000000000000 yocto = 0.0070001 NEAR. This matches the 2026-11-03 record exactly.
- Explicit 1B instructions, 128 MB, 30 s: 4000100000000000000000 = 0.0040001 NEAR.
- input_len 100: same as defaults. input_len 40000: 79320100000000000000000 = 0.0793201 NEAR, which is 0.0070001 plus 7232 bytes over 32 KB at 0.00001 NEAR per byte, matching the documented rule exactly.
- `get_execution_cost` does not exist: MethodNotFound, re-verified live.

The estimate does not include compile time. The charge on resolve is the base fee plus instructions used times the per-million-instructions fee (integer division) plus execution time times the per-millisecond fee, capped at the compute deposit. Compile time can push the cost past the compute deposit, and the cap keeps `total_fees_collected` honest. Pricing read live from `get_pricing` (views.rs line 17): base fee 1e21 yocto (0.001 NEAR), per-million-instructions fee 1e14, per-ms fee 1e17, per-compile-ms fee 1e17. The charge formula (`calculate_cost`, lib.rs line 807) is base + (instructions / 1,000,000) x per-million fee + time_ms x per-ms fee + compile_time_ms x per-compile-ms fee, with integer division on instructions. It reproduces all three observed charges exactly: 10177 (0.0010296 NEAR), 10178 (0.0020587004 NEAR), 10270 (0.0012895022 NEAR). Note 331,394 instructions cost nothing because 331394 / 1,000,000 is 0 in integer division.

Live run cost: neither of our two requests produced a successful execution, so there is no successful-run charge to report for them. The retry (request 10262) was charged only the base fee, 0.001 NEAR, with 0.099 NEAR refunded. Neighbouring successful executions in the same windows show what a working run costs: request 10177 (VRF) charged 0.0010296 NEAR, 331,394 instructions, 296 ms; request 10178 (price oracle) charged 0.0020587004 NEAR, 4,315,158 instructions, 3,234 ms, compile 7,353 ms; request 10270 (game, combined flow) charged 0.0012895022 NEAR, 22,998,939 instructions, 2,895 ms, compile cached. So a successful verification would cost roughly 0.001 to 0.0021 NEAR. See section 9 for the full receipts.

## 6. Timeout behavior

`EXECUTION_TIMEOUT` is 600 seconds (10 minutes), from the contract source. After it passes, the original sender can call `cancel_stale_execution(request_id)` and gets a refund minus a charge: the base fee if no output was delivered, or the compute estimate if output was delivered through the 2-call flow but the callback never settled it. The owner's `emergency_cancel_execution` remains and refunds in full. Hard caps: 500 billion instructions, 180 seconds execution, 300 seconds compilation, 4096 MB memory. The resume data through `promise_yield_resume` is limited to 1024 bytes (execution.rs line 1075: 'This avoids the 1024 byte limit of promise_yield_resume'; the limit is the NEAR protocol's cap on yield-resume data, referenced in the contract source); larger outputs go through the 2-call flow (`submit_execution_output` then `resolve_execution`, or the combined `submit_execution_output_and_resolve`) and are read back from state.

## 7. Whether the worker measurement equals the app WASM hash

No. They are measurements of different things, bound together by the per-execution quote.

- The worker measurement is the TDX measurement of the worker's confidential VM: five values (MRTD + RTMR0-3) covering firmware, kernel, boot configuration, and the application compose (RTMR3). The attestation record carries it as `worker_measurement`.
- The app WASM hash is the SHA-256 of the guest WASM binary. It appears in the per-execution quote's task hash (section 3), not in the worker measurement.
- The quote therefore proves: this approved worker build ran this task, where the task names this WASM hash, this input hash, and this output hash. The worker measurement and the WASM hash are different values; the quote binds them together for one execution. Anyone who checks only the worker measurement has not checked which code ran, and anyone who checks only the WASM hash has not checked which worker ran it.

## 8. What the vault can verify, within gas and storage limits (contract)

- The vault CAN verify a VRF result on-chain: `env::ed25519_verify` at about 1 TGas, plus JSON parsing of the output. That fits easily in a 10 TGas callback allocation (the DAO example uses exactly that). Storage is a 32-byte public key and the request binding. This is the only OutLayer result with on-chain authentication of the result bytes themselves.
- The vault's callback must follow the NEAR callback invariants: it is `#[private]`, it takes the result as `Result<Output, PromiseError>`, where Output is the parsed output per response_format (the guest's JSON for Json, a string for Text, base64 for Bytes, or null when the run failed), not the ExecutionResponse. OutLayer's own `on_execution_response` takes `Result<ExecutionResponse, PromiseError>` and returns the parsed output to the caller via `env::value_return`, so a vault callback written to the ExecutionResponse type would fail to deserialize. It handles a promise error or a null output without panicking, and it records the pending request in state before calling `request_execution` and checks in the callback that the request is still pending and has not already timed out or been escalated. A callback that panics or trusts an unrecorded request is a hole, not a verification. These are the frozen Cynex callback rules (docs/contract-api.md; the vault's own callbacks already follow them).
- In VRF mode, `ed25519_verify` alone is not enough: the vault must also check that the alpha's `request_id`, `sender_id`, and `user_seed` match the pending request it recorded. Otherwise a valid VRF signature from a different request (for example request 10177, which resolved successfully in the same window) would pass verification and be accepted as the answer to this request. The alpha is taken from the output unchanged, never rebuilt, and its fields are matched before the signature is trusted. The vault must also recompute SHA256(signature) and compare it to the returned value.
- OutLayer's generic flow does not verify a TDX quote on-chain. The contract does not attempt it, and the vault has no such check either. This report does not claim it is impossible in principle, only that no path in the flow as built does it. The generic flow's on-chain check is predecessor-is-operator only.
- So an honest integration has two shapes and no third: (a) VRF mode, where the vault accepts a result only if its Ed25519 signature verifies against the known VRF public key, with the alpha taken from the output unchanged, never rebuilt; (b) operator-trust mode, where the vault accepts the callback because it came from the operator account, and says so plainly. Mode (b) is not verification, it is trust in the operator account and its key registration, and the UI must label it that way.
- In the plan's frozen trust-mode names (section 3.1.8): the plan lists four labels, `ON_CHAIN_ATTESTATION_VERIFIED` (only if truly verified), `OUTLAYER_CALLBACK`, `TRUSTED_RELAYER`, `FIXTURE`, without defining `OUTLAYER_CALLBACK` precisely, so this mapping is the report's reading, not a definition from the plan. Mode (a) is read as `OUTLAYER_CALLBACK`, the callback carrying a result the vault verifies on-chain. Mode (b) is not `OUTLAYER_CALLBACK` as a verification; it is trust in the operator account, and showing it under that name would mislabel it. `ON_CHAIN_ATTESTATION_VERIFIED` would require the attestation itself to be verified on-chain, which no flow in this spike achieves: the TDX quote is not verified on-chain, and the VRF mode verifies an Ed25519 signature over the output, not the attestation. `TRUSTED_RELAYER` is the current verifier and stays the mode shown. `FIXTURE` is test fixtures only and is never shown as a live mode.
- The current verifier is TRUSTED_RELAYER. OutLayer does not replace it by default. If OutLayer is integrated, the UI must show exactly one trust mode, and the mode shown must be the one the code actually enforces.

## 9. The live runs

Two live `request_execution` calls were made from `cynexmaster.testnet`, both with the same GitHub source (public repo `out-layer/vrf-example`, commit `419789883f9020e8f64d01116d679d4e72ef2fd5`, build target `wasm32-wasip2`), `resource_limits` `{}`, `response_format` `Json`, deposit 0.1 NEAR. Both calls were signed by cynexmaster.testnet with its full-access key; the agent's scoped settle-only key could not have made them. Both produced no verifiable execution.

### Request 10176 (first attempt)

- Submitted 09:56 UTC, tx `CxxHAdsTCqXpySFHXP6XjSd6qPHN7ZxivBzPu9nMwnKa`. Input `{"seed":"cynex-spike","count":1,"max":1}`. Confirmed pending via `get_request` with the exact args, payment 0.1 NEAR.
- It is no longer pending (`get_request` null, pending list empty). But no worker `resolve_execution` transaction for it exists: every worker resolve in the indexed range 09:17 to 11:01 UTC was read and its `request_id` decoded, and the resolved sequence runs 10177 to 10256 with 10176 the sole gap in that window. A second check of the resolves after 11:04:19 UTC runs 10263 to 10280, with 10262 the sole gap there. No cancel transaction from the sender or the owner exists in their indexed transactions. No attestation was published for 10176 (`GET /attestations/by-request/10176` returns 404 on the testnet host, while neighbours 10170 to 10175 return 200 with full TDX quotes, as do older requests 91 and 93). The leading explanation for how it left pending is the NEAR yield timeout: a yield that is never resumed times out after about 200 blocks and runs the callback with a `PromiseError`, which removes the request, keeps the base fee, and refunds the rest. That is exactly the path observed in request 10262's own receipts (promise failed, 0.001 NEAR kept, 0.099 NEAR refunded), so the mechanism is proven for the retry; for 10176 itself no receipt was captured, so the timeout is the leading explanation, not a proven fact. Separately, the worker source contains a bail, "Building from a GitHub repository is not available on this worker", which is the leading hypothesis for why it was never picked up, but that is a hypothesis, not a proven cause.
- The poller that reported it resolved at 09:58:45 was wrong: its `get_request` call failed during an RPC outage and it read the failure as null. The request was still pending at 09:58:14 and the three completions counted by then were 10177, 10178, and 10179, not mine. Lesson recorded: a failed view call must never be read as a null result.

### Request 10262 (retry, same source)

- Submitted 11:04:19 UTC, tx `Ebeuanhvi4nY8ERYKeV86PWHqTkDeu4jBJg3TKUFpyy`. Input `{"seed":"cynex-spike-2","count":1,"max":1}`. The `execution_requested` event confirms request_id 10262, sender `cynexmaster.testnet`, the same GitHub source.
- Its receipts show the callback ran with a promise error (receipt `3faXQZoEZTJMoj6fVpu63Eo14bKD4TErbVMzPXEMzqTe` in the submission tx's receipts_outcome): "Execution promise failed: Failed. Refunded 99000000000000000000000 yoctoNEAR". Charged only the base fee, 0.001 NEAR; 0.099 NEAR refunded; return value null. No output, no VRF value, no signature.
- No attestation was published for it either: `GET /attestations/by-request/10262` returns 404, as it does for 10176.
- The worker never sent a resolve for it either: the worker resolves after 11:04:19 UTC run 10263 to 10280 continuously, with 10262 missing. But 10262 is not a silent drop like 10176: it ended in a visible failure, the promise error in its own receipts. What the two attempts share is that the worker never resolved either GitHub-source request while resolving every neighbouring request.
- One caveat to this finding: both of my calls were made directly from an account (near-cli), not from a calling contract. The documented VRF and DAO examples call `request_execution` from a contract, which is how the vault would call it. Whether a contract caller would have fared better is not proven by these two attempts, because the worker never attempted a resolve for either. The worker never sent a resolve_execution for either request before the yield callback ran, which is consistent with a worker-side refusal, but it does not rule out the direct-call difference: a worker that rejects non-contract callers would also skip before any callback, so the evidence does not settle which it is.

### What others' executions show

- The worker is live and busy: it resolved requests 10177 to 10280 in the same period, with 10176 and 10262 the only gaps (10257 and 10261 went through the combined `submit_execution_output_and_resolve` flow, tx `AfKjiaQWfZpjPpSbSxCcKDJ2dUQfuZ95oCWd3dKbW9qG` and tx `H75oASPbP7uNgjZ8NvU44CrCASh3U6uu8n8VPjeU8Mbx`; the rest through `resolve_execution`), including a VRF-style run (10177, success true, charged 0.0010296 NEAR, instructions 331394, time 296 ms, resolve tx `BgYEdn28QUq24xHnAf9T1wxikSLxoaSzo1wTyeGm8oMt`) and a price-oracle run (10178, success true, charged 0.0020587004 NEAR, instructions 4315158, time 3234 ms, compile 7353 ms, freshly compiled, resolve tx `7cK8UNs5gFy8fGXpYg9SBHdrksPGtVXSZEk3sng49ivS`). A game execution (10270) resolved through the combined flow with output stored in state, charged 0.0012895022 NEAR, instructions 22998939, time 2895 ms, compile cached (compilation note "Cached WASM from 2026-11-03T20:43:19", resolve tx `CXNvPVVBWJfhqek6Dxr5FeAPBrV9CwUvH9nwheciPTeb`). So a successful verification would cost roughly 0.001 to 0.0021 NEAR, which is cheap. Cost is not the blocker. Reliability of the path for our source is.
- Failed executions do get resolved with `success: false` (requests 10255, resolve tx `7zjqdbdTu3x5zMmwuANoTgDpUVaBRgnnU9THv8WCuqL7`, and 10256, resolve tx `3FTtndvj3rDWez5oxm5MXRW5MTfFpAfHe71KBH9LnTHh`), so a failure is normally observable. Mine were not resolved by the worker: 10176 ended in a silent drop and 10262 in a yield-timeout promise error, rather than a worker `resolve_execution` with `success: false`.

## 10. FastFS upload: no-go

- Built a tiny zero-dependency wasip1 verifier guest (80,847 bytes, SHA-256 `528f5c78da9fd97698f20eb21a5e405aa9aa6aec54ee17218b1060549e3725b6`) in `the workspace-build-tmp/outlayer-spike`.
- Uploaded it to FastFS three times with the documented Borsh format (method `__fastdata_fastfs`, receiver `outlayer.testnet`, deposit 0): tx `3YHTj7wgApHyfwq8s4wh5LCRG7z7Gs3HwM7N9AJKaTdS` (300 TGas, MethodNotFound), tx `6iVwQuqxyJaHzVQX1ZnxfFcrTxBiNUkZbSxFcKj6DZ5g` (repeat), tx `EzeSkk7mcL8TNsthHdx43maTdmLkBc3mcvp1zJXdX1r9` (gas 1, "Exceeded the prepaid gas", exactly as the CLI docs describe). All three are on chain with the correct args (80,949 payload bytes, Borsh verified). None is served at either documented URL form (`test.fastfs.io/cynexmaster.testnet/outlayer.testnet/<hash>.wasm` or `cynexmaster.testnet.fastfs.io/outlayer.testnet/<hash>.wasm`) after 35+ minutes, all 404. All three calls FAILED at the NEAR level (MethodNotFound twice, "Exceeded the prepaid gas" once). The FastFS CLI docs describe the gas-1 failure as the expected upload pattern, because the indexer reads the transaction args rather than contract state, so a failed call does not by itself mean nothing was submitted. But none of the files is served at either documented URL form after 35+ minutes, all 404, and no known-good testnet FastFS URL exists to cross-check against. So the cause is undetermined: the submission may have the wrong receiver, method, or args, or the testnet indexer may be down or not indexing. Either way the WasmUrl path was never successfully exercised, and it is blocked until an upload is shown to be served. The calls themselves are on chain in the documented Borsh format (method `__fastdata_fastfs`, format from `worker/src/fastfs.rs` in fastnear/near-outlayer; their args decode to 80,949 payload bytes), so the submission format is checkable even though the calls failed.

## 11. Verdict: do not integrate

At the time of this spike, OutLayer was not integrated into Cynex, and `TRUSTED_RELAYER` remained the single trust mode shown.

The reasons are the live findings, not the theory. Both ways to supply our own WASM failed to produce a verifiable execution: the FastFS upload path was never successfully exercised (three on-chain upload calls, all failed at the NEAR level, files never served), and the GitHub build path produced no execution in two attempts while the worker resolved every neighbouring request. No attestation was published for any of the requests I made and checked, so a success in my two attempts would have lacked the published quote the trust story needs. The endpoint does publish quotes for older successful requests (91 and 93 returned 200 with full TDX quotes), and for the neighbours of 10176, so the gap is specific to requests 10176 and 10262, not a general absence. The contract and the attestation design read well in the source, but the live evidence is what matters and it does not support integration, and a successful run would cost only about 0.001 to 0.0021 NEAR, but a verifier that drops one request without a visible failure and fails the other without output, signature, or attestation is not something the trust story can stand on.

What would change this: a contract-caller execution (from the vault, not a direct call) that resolves with a VRF output whose Ed25519 signature verifies against the published testnet public key (`c0c5aeae1688c2f7cc2350aae1ee3ce96eddc0de84d678db873de48268f8cfa8`, read live from https://testnet-api.outlayer.ai/vrf/pubkey), plus a published attestation for the same request id (at https://testnet-api.outlayer.ai/attestations/by-request/{request_id}). This acceptance test has since been met (requests 10640, 11912, 13040 and 13324), which is why the verdict above is superseded. OutLayer is now integrated, not a documented spike. The report keeps the sourced design answers above so a future attempt does not have to re-derive them.
