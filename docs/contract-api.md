# Cynex contract API, frozen 2026-11-03

Version: cynex-v1.0.0, schema in schemas/cynex-v1.0.0, test vectors in tests/test-vectors/vectors.json.

This document is the no-clash contract between contract and frontend. Both sides build against exactly what is written here. A change to anything in this file needs sign off from both sides, and a change to the schema or the digest needs new test vectors that both languages reproduce byte for byte. Nothing in this file is left vague. Where a value is not yet measured, it is marked TBD in plain sight, and the side that must fill it is named.

Network: testnet throughout. The settlement digest uses the literal network id testnet, and the digest function rejects any other network id. Mainnet would be a new domain and a new schema version, not a quiet edit here.

## Types

All amounts are u128 base units. Token amounts use 6 decimals, read from ft_metadata, so 250.000000 USDC.e is 250000000 base units. All timestamps and expiries are u64 nanoseconds. Use BigInt for every u64 and u128 value in TypeScript, without exception, because nanosecond timestamps are far above 2 to the power of 53 and a plain JS Number would silently lose precision.

Policy: policy_id (string), owner (account id), token_id (account id), limit (u128), spent (u128), reserved (u128), funded (u128), frozen (bool), version (u64), reconciler (account id or null). Funded is the amount credited to this policy by ft_on_transfer, never the vault account balance. A policy with no reconciler is owner only for timeout and resolution.

Obligation: obligation_id (string), policy_id (string), policy_version (u64, recorded at creation from the policy version at that time), recipient (account id), amount (u128), evidence_type (string), evidence_hash (32 bytes), expires_at_ns (u64), nonce (u64), state (ObligationState), in_flight (bool, true only while a transfer promise is outstanding), transfer_attempt (u64, starts 0, increments by 1 on each dispatch, used to reject stale callbacks), transfer_dispatched_at_ns (u64 or null, set only on dispatch, cleared on callback or resolution), pending_request_id (string or null), pending_digest (32 bytes or null), evidence_requested_at_ns (u64 or null, set only by request_evidence).

Receipt: index (u64), prev_hash (32 bytes), obligation_id (string), recipient (account id), amount (u128), token_id (account id), timestamp (u64), tx_ref (string).

ObligationState: CREATED, EVIDENCE_PENDING, WARN_PENDING, READY, TRANSFER_PENDING, PAID, BLOCKED, CANCELLED, RECONCILIATION_REQUIRED.

EvidenceResult: ALLOWED, WARN, BLOCK.

ReasonCode: RECIPIENT_SUBSTITUTION, TERMS_MISMATCH, NONCE_ALREADY_CONSUMED, BUDGET_EXCEEDED, OBLIGATION_EXPIRED, POLICY_FROZEN, VAULT_STORAGE_EXHAUSTED, EVIDENCE_MISMATCH, EVIDENCE_EXPIRED, UNAUTHORIZED_VERIFIER.

TrustMode: ON_CHAIN_ATTESTATION_VERIFIED, OUTLAYER_CALLBACK, TRUSTED_RELAYER, FIXTURE. A trust mode is never silently downgraded. FIXTURE is only ever a test label, never a production claim.

Token ledger invariant, checked with checked arithmetic and overflow-checks true: spent plus reserved plus amount must be less than or equal to limit, per policy, and also less than or equal to funded, per policy. The vault token ledger for a token is funded as credited deposits across policies for that token, with spent and reserved as allocations against that funded amount, never the vault account balance alone. Available for a policy is funded minus spent minus reserved, and policies sharing a token do not share each other funding. Native NEAR headroom is checked separately and is never summed with token units.

Policy version: version increments only on an owner approved policy change, never on freeze or unfreeze. Freeze sets the frozen flag only, so a freeze and unfreeze cycle does not permanently block obligations created before it. There is no update_policy method in this version. If a policy term must change, freeze the old policy and create a new one, with a new policy_id. Settle checks that the obligation recorded policy_version equals the policy version at settle time, and that the policy is not frozen. A mismatch rejects, because the terms the obligation was created under are no longer the current policy terms.

Nonce: one nonce per obligation, supplied by the owner at create_obligation, locked on dispatch, not permanently consumed on dispatch. Its job is to make a duplicate settle call detectable as NONCE_ALREADY_CONSUMED even while the first attempt is still in flight, where obligation id plus PAID state alone would not cover that case. The lock is held only while in_flight is true. On a confirmed transfer failure the lock is released, the nonce is reusable for a retry, and the obligation returns to READY settleable. On PAID the nonce is permanently consumed, because PAID is terminal. The nonce does not replace state checks.

Pending evidence fields: pending_request_id is the id the verifier must echo in submit_evidence. pending_digest is the settlement digest that evidence must bind to. Evidence for a different request id or digest is rejected.

## Settlement digest

Domain tag first, as raw ASCII: CYNEX_SETTLEMENT_V1. Then, in this exact order: network_id, vault_id, policy_id, policy_version, obligation_id, token_id, recipient, amount, evidence_type, evidence_hash, nonce, expiry.

Encoding: every string field after the domain tag is a u32 big-endian length prefix followed by UTF-8 bytes. Integers are fixed width and big-endian: policy_version, nonce and expiry are u64, amount is u128. evidence_hash is raw 32 bytes, with no length prefix. The hash is SHA-256 over the whole encoding.

The Rust and TypeScript implementations must reproduce the six vectors in tests/test-vectors/vectors.json byte for byte. Any hash mismatch in either language blocks acceptance. Numbers in the vectors file are strings, so no language may parse them as a floating point number.

## Receipt hash

Receipts are stored in contract state and emitted as NEP-297 events. The receipt hash is a different hash from the settlement digest, for a different purpose, and the two must never be interchanged.

receipt_hash equals SHA-256 over: index as u64 big-endian, then prev_hash as raw 32 bytes, then obligation_id with a u32 big-endian length prefix and UTF-8 bytes, then recipient the same way, then amount as u128 big-endian, then token_id the same way, then timestamp as u64 big-endian, then tx_ref the same way.

The genesis receipt uses prev_hash as 32 zero bytes. Each later receipt uses the previous receipt hash as its prev_hash, so the chain can be replayed from genesis and any gap or tamper shows up.

## Methods

Owner means predecessor equals owner. Owner actions are signed by the owner wallet or CLI, never by the executor host. Reconciler means the account recorded in the policy reconciler field, which starts None at policy creation and is changed only by the owner via set_reconciler. If the field is null, only the owner may call timeout and resolution methods. A reconciler may only call the two timeout methods, never owner only methods, and never resolve_settlement to any outcome, see below.

create_policy(policy_id, token_id, limit): caller owner. Creates a policy with spent 0, reserved 0, funded 0, frozen false, version 1, and reconciler None. Reconciler is changed only by set_reconciler, never at policy creation. set_reconciler(policy_id, reconciler): caller owner. Changes only the reconciler field, it does not bump version and does not change terms. The reconciler argument is an account id or null: null clears the reconciler back to owner-only resolution.

create_obligation(policy_id, obligation_id, recipient, amount, evidence_type, evidence_hash, expires_at_ns, nonce): caller owner. Creates an obligation in CREATED, with the caller-supplied nonce recorded as given, policy_version copied from the policy at creation, in_flight false, and no pending evidence and no evidence request time. The nonce is used in pending_request_id, as obligation_id plus a hyphen plus the nonce, and in the settlement digest. The recipient, amount, evidence type, evidence hash and expiry recorded here are the authoritative terms. Nothing the agent later proposes can change them. Create rejects a zero amount with TERMS_MISMATCH, an expires_at_ns at or before the current block timestamp with OBLIGATION_EXPIRED, and an evidence_type outside PREIMAGE, TEE, and delivery-note with EVIDENCE_MISMATCH.

freeze_policy(policy_id): caller owner. Sets frozen true only, it does not bump version. New settle calls are blocked while frozen. A transfer already in flight is not un-booked by a freeze. unfreeze_policy(policy_id): caller owner. Sets frozen false only, it does not bump version, and obligations created before the freeze become settleable again if their recorded version still matches and they are in READY.

cancel_obligation(obligation_id): caller owner. Allowed from CREATED, RECONCILIATION_REQUIRED, BLOCKED, and WARN_PENDING, otherwise ERR_INVALID_STATE. Expiry alone does not auto-cancel, because auto-cancel would hide a missed settlement.

approve_warning(obligation_id): caller owner. Moves WARN_PENDING to READY.

add_verifier(account_id): caller owner. Adds an account to the allowlisted verifier set. The set starts empty, and evidence cannot be submitted until at least one verifier is added.

remove_verifier(account_id): caller owner. Removal takes effect immediately for new submissions, and never retroactively for evidence already accepted.

settle(obligation_id, proposed_recipient, proposed_amount, evidence_ref): caller agent through a scoped function call key, or anyone. This is the checked parameter signature, frozen as written. The vault reads the authoritative terms from state and rejects any mismatch on chain with a reason code. A proposed recipient that differs from the recorded recipient rejects with RECIPIENT_SUBSTITUTION. A proposed amount that differs rejects with TERMS_MISMATCH. An id only settle is not an alternative signature, because a bad payee would never reach the contract and the demo rejection would not be real.

Settle checks, in order, before any promise: nonce first, then state, then recorded terms against proposed terms, expiry against expires_at_ns, policy not frozen, obligation recorded policy_version against policy version, token lock, then the budget invariant spent plus reserved plus amount less than or equal to limit and also less than or equal to funded, then native NEAR headroom. The nonce check runs before the state check: in_flight true rejects with NONCE_ALREADY_CONSUMED, state PAID rejects with NONCE_ALREADY_CONSUMED, any other non-READY state rejects with ERR_INVALID_STATE. A duplicate settle is therefore detectable as NONCE_ALREADY_CONSUMED even while the first attempt is still in flight, which is what the frozen nonce paragraph promises. Before the state check came first, so a duplicate settle always hit ERR_INVALID_STATE and the nonce code was unreachable. The later in_flight require after the policy version check was removed as unreachable, with a comment noting the move. No other check changed order or code. ERR_INVALID_STATE is the pre-existing generic state-machine code, not one of the six settle reason codes, and is unchanged by this change. The nonce is still not permanently consumed on dispatch. On a confirmed transfer failure the lock releases, the nonce is reusable for a retry, and the obligation returns to READY, while transfer_attempt is below MAX_TRANSFER_ATTEMPTS, 3. At 3 confirmed failures the obligation escalates to RECONCILIATION_REQUIRED instead, with reservation, in_flight, dispatch time, and token lock retained, and no public resume. Only PAID consumes the nonce permanently, and a READY resolution through resolve_settlement marks it consumed too, so that obligation can never settle again and a genuine retry needs a fresh obligation. RECONCILIATION_REQUIRED keeps in_flight true by design, mark_reconciliation_required changes only the state, so a settle there reports NONCE_ALREADY_CONSUMED, which is correct, the nonce is still locked while the transfer outcome is unresolved. in_flight can only be true in TRANSFER_PENDING and RECONCILIATION_REQUIRED. Only then does it write reserved plus amount to both the policy and the token ledger, set TRANSFER_PENDING and in_flight true, increment transfer_attempt by 1, set transfer_dispatched_at_ns to the current block timestamp, and lock the nonce, all synchronously before the promise is returned. The callback for that dispatch is created with obligation_id and the new transfer_attempt as its arguments, so a callback for an older attempt can never book a newer one. Waiting until the callback to reserve would let two concurrent settle calls both pass the budget check and both pay.

request_evidence(obligation_id): caller owner. Moves CREATED to EVIDENCE_PENDING only. It rejects on a frozen policy with POLICY_FROZEN and on an already-expired obligation with OBLIGATION_EXPIRED. sets pending_request_id to obligation_id plus a hyphen plus the nonce as a decimal string, sets pending_digest to the settlement digest computed from the recorded terms, recorded policy_version, and nonce, and sets evidence_requested_at_ns to the current block timestamp. No other method sets these fields, and no evidence can be submitted before this call. submit_evidence(request_id, obligation_id, result, proof): caller predecessor in the allowlisted verifier set. This method is deliberately not private, because a relayer or OutLayer must be able to call it. Proof is the hex string of the SHA-256 of the artifact the verifier checked, it must equal the obligation evidence_hash or the call rejects with EVIDENCE_MISMATCH, the request id must equal pending_request_id, the settlement digest for the recorded terms must equal pending_digest, and a result submitted after expires_at_ns rejects with OBLIGATION_EXPIRED. A result submitted after evidence_requested_at_ns plus EVIDENCE_TIMEOUT_NS, 3600000000000 nanoseconds, 1 hour, also rejects with ERR_EVIDENCE_EXPIRED, even if nobody called mark_evidence_timeout first; at exactly requested plus EVIDENCE_TIMEOUT_NS submit still accepts, one nanosecond later it rejects. On a successful submit all three pending fields are cleared: pending_request_id, pending_digest, and evidence_requested_at_ns, on ALLOWED to READY, WARN to WARN_PENDING, and BLOCK to BLOCKED. If state is EVIDENCE_PENDING and evidence_requested_at_ns is missing, submit_evidence panics ERR_INVALID_STATE instead of silently skipping the timeout check. Result is EvidenceResult: ALLOWED moves the obligation to READY, WARN moves it to WARN_PENDING, BLOCK moves it to BLOCKED. BLOCKED has no exit except owner cancel: approve_warning runs only from WARN_PENDING, cancel_obligation runs from CREATED, RECONCILIATION_REQUIRED, BLOCKED, or WARN_PENDING, and no funds are locked in BLOCKED, request_evidence holds no reservation, so it is a dead record, not locked funds. A predecessor outside the allowlist rejects with UNAUTHORIZED_VERIFIER. An obligation whose evidence_type is "PREIMAGE" rejects here with ERR_EVIDENCE_MISMATCH; it can only be verified through submit_evidence_preimage, so a verifier cannot mark it READY with a hex proof alone. An obligation whose evidence_type is TEE rejects here the same way; it can only be verified through the TEE guest plus VRF, so a verifier cannot bypass that check with a hex proof.

submit_evidence_preimage(request_id, obligation_id, evidence): , layer 1, built and unit-proven (69 tests), committed as 42c9bf6, deployed to the test vault and proven live 2026-11-06 (correct bytes go READY, wrong bytes reject with ERR_EVIDENCE_MISMATCH and leave the state unchanged). Caller anyone, permissionless, the caller is a courier, not a judge. Only obligations whose evidence_type is "PREIMAGE" accept raw bytes, any other type rejects with ERR_EVIDENCE_MISMATCH and must use the verifier path, and the reverse holds too: submit_evidence rejects a PREIMAGE obligation, so the bytes are the only way to verify it. Evidence over MAX_PREIMAGE_BYTES, 65536 bytes, rejects with ERR_EVIDENCE_TOO_LARGE. The request id must equal pending_request_id, the settlement digest for the recorded terms must equal pending_digest, a submit after expires_at_ns rejects with ERR_OBLIGATION_EXPIRED, and a submit after evidence_requested_at_ns plus EVIDENCE_TIMEOUT_NS, 3600000000000 nanoseconds, 1 hour, also rejects with ERR_EVIDENCE_EXPIRED, same rules as submit_evidence. The vault computes env::sha256 over the bytes itself and compares the result to the obligation evidence_hash; a mismatch rejects with ERR_EVIDENCE_MISMATCH and changes no state. On a match the obligation moves to READY and all three pending fields are cleared: pending_request_id, pending_digest, and evidence_requested_at_ns. The bytes are hashed and dropped, never stored, so this adds no storage. A hash match is the verdict, there is no WARN or BLOCK outcome on this path. Gas measured live on the test vault, 2026-11-06: submit_evidence_preimage vault receipt 1.81 TGas.
request_tee_verification(obligation_id, evidence_url): , layer 2, written, unit-proven (94 tests), deployed to the test vault 2026-11-06; layers 2 and 3 failed the first live proof on the VRF sender check (the alpha sender is the transaction signer, not the vault), the sender fix is applied and unit-proven, and the live re-proof PASSED on request 10640 (the same obligation p9-live-tee-001 went READY, seed counter 1, VRF signature verified, attestation served with matching input and output hashes). Caller owner only, because the call attaches NEAR for the OutLayer execution and anyone could drain the vault by spamming it. The obligation must be EVIDENCE_PENDING with evidence_type TEE, inside its evidence window: a call after expires_at_ns rejects with ERR_OBLIGATION_EXPIRED, and a call after evidence_requested_at_ns plus EVIDENCE_TIMEOUT_NS, 3600000000000 nanoseconds, 1 hour, rejects with ERR_EVIDENCE_EXPIRED. Only one TEE request at a time per obligation; a second request while one is pending rejects with ERR_INVALID_STATE. The vault must hold at least TEE_REQUEST_DEPOSIT_YOCTO, 0.01 NEAR, plus the settle headroom in liquid headroom, balance minus storage already used, or the call rejects with ERR_VAULT_STORAGE_EXHAUSTED. The vault records a TeeRequest (obligation id, evidence URL, seed, requested time, sender) under a separate trie prefix, so the Contract and Obligation structs are unchanged and no migration is needed, then calls outlayer.testnet request_execution with the Project source cynexmaster.testnet/cynex-verifier (active version), the input JSON with the URL and the seed (obligation id plus hyphen plus nonce plus hyphen plus a monotonically increasing request counter plus hyphen plus the committed digest in hex, so the seed is unique per request and bound to the evidence the vault committed to; the counter lives under its own trie prefix, so the Contract struct is unchanged and no migration is needed; a signature from an earlier execution for the same obligation does not match a retry's recorded seed even when the retry lands in the same block and shares the timestamp, and a signature from a different obligation or a different digest cannot be reused here), resource limits 1B instructions, 128 MB, 60 seconds, response_format Json, and a 0.01 NEAR deposit, and attaches the private callback on_tee_result. The guest fetches the evidence from the URL, hashes it with SHA-256, requests VRF randomness, and returns digest, source, request id, VRF output, signature, and alpha. on_tee_result(obligation_id, result): , layers 2 and 3, private, called only by the vault itself through the yield promise. The result is the guest output parsed as JSON, or null when the run failed, and the callback takes Result<serde_json::Value, PromiseError>, never Result<ExecutionResponse, PromiseError>. A stale result (obligation missing, no TeeRequest, or state no longer EVIDENCE_PENDING), a result after expiry or after the evidence timeout, a promise error, or a null output changes nothing and drops the TeeRequest record, including on the stale-state path, so the owner can retry; the callback never panics and never books anything on failure. On a value it verifies three things, and all must pass: the digest matches the committed evidence_hash, the source matches the recorded evidence URL, and the VRF checks (the alpha is vrf:{request_id}:{sender}:{seed} with the sender the transaction signer who filed the request, recorded in the TeeRequest, and the seed the recorded one, the Ed25519 signature verifies against the testnet VRF public key, and SHA-256 of the signature equals the returned output). The sender is the signer, not the vault: proven live on request 10522, where sender_id was cynexmaster.testnet and predecessor_id was the test vault, and an earlier version that required the vault itself failed the live callback for exactly this reason. On a pass the obligation moves to READY and all three pending fields are cleared: pending_request_id, pending_digest, and evidence_requested_at_ns. The VRF signature is consistent with a TEE guest having run for this specific request and this specific digest, and the vault checks the returned digest against the commitment. It does not by itself prove the guest fetched the bytes, and the code verifies an Ed25519 signature over an alpha, not a per-execution TDX quote; the claim that the guest fetched from the source rests on the guest being our code, pinned by version_key to one exact guest build, and on the per-execution TDX quote, which is verified off-chain: the attestation endpoint serves real quotes, verified live for requests 10522 and 10640 with matching input and output hashes. The contract runtime has no TDX quote verification primitive, so the VRF signature is the on-chain anchor. The request pins version_key to 8abfe08bc62919dd3f0aea2c2ea5dbe91d5484c14d6a55289053dce1d0387a6f, the active guest version's full wasm hash, confirmed live on testnet, so the execution runs exactly that guest build. A TEE obligation that times out can still be escalated by the owner to WARN_PENDING and approved to READY by a human, which is a deliberate owner action, not an agent bypass; the TEE-only claim holds for the agent and verifier paths, with that human exception. The VRF public key is the testnet one at https://testnet-api.outlayer.ai/vrf/pubkey; testnet and mainnet have different keys, and the mainnet key does not verify a testnet signature. ft_on_transfer(sender_id, amount, msg): caller the configured token only, through ft_transfer_call. This is the only funding path, see Funding below.

on_transfer_complete(obligation_id, attempt_id): private, called only as the callback on this contract, with callback result Result<(), PromiseError>. ft_transfer returns unit, so the result carries no value. It acts only if the obligation is still TRANSFER_PENDING, in_flight is true, and attempt_id equals the current transfer_attempt, otherwise it returns without changing state, spent, reserved, or receipts, so a late or stale callback cannot double book or undo a resolution. On Ok, reserved minus amount, spent plus amount, state PAID, append receipt, clear in_flight, clear transfer_dispatched_at_ns, nonce permanently consumed. On Err, confirmed failure, tokens did not move: while transfer_attempt is below MAX_TRANSFER_ATTEMPTS, 3, release reservation and lock, unlock the nonce for a retry, clear in_flight, clear transfer_dispatched_at_ns; at 3 confirmed failures move to RECONCILIATION_REQUIRED instead, retaining reservation, in_flight, dispatch time, and token lock. If the policy is frozen at callback time, a failure moves the obligation to RECONCILIATION_REQUIRED for an owner decision, it does not move to CANCELLED, because cancel_obligation does not allow TRANSFER_PENDING and freeze never un-books an in-flight transfer. A success always finalizes to PAID even if the policy was frozen in the meantime. Failure alone never cancels.

mark_reconciliation_required(obligation_id): Implemented. Caller owner or the policy reconciler. Moves TRANSFER_PENDING to RECONCILIATION_REQUIRED, only after TRANSFER_TIMEOUT_NS has passed since transfer_dispatched_at_ns, and only from TRANSFER_PENDING. It keeps in_flight true, keeps the reservation held, and does not release the nonce lock, so no retry can happen while the original transfer might still succeed. Rejects otherwise. This exists because a NEAR contract cannot move itself on a timer.

mark_evidence_timeout(obligation_id, escalate): caller owner or the policy reconciler. Moves EVIDENCE_PENDING only, and only after EVIDENCE_TIMEOUT_NS has passed since evidence_requested_at_ns. If escalate is false it moves to CANCELLED, if escalate is true it moves to WARN_PENDING. All three pending fields are cleared, and any TeeRequest record for the obligation is dropped too, so a TEE request in flight is abandoned with the obligation and a late callback finds nothing to resolve. Evidence that never arrives never moves an obligation to READY by default.

resolve_settlement(obligation_id, outcome, proof): Implemented. Caller owner for PAID, READY, or CANCELLED; the policy reconciler can no longer resolve to any outcome. Resolves RECONCILIATION_REQUIRED only, with in_flight still true and the reservation still held, after a timeout. Proof is the transaction hash of the transfer as seen on chain, recorded as the receipt tx_ref for a PAID resolution, plus the caller attestation that is the on chain call itself. The contract cannot verify a transaction hash alone on NEAR, so for PAID the owner must first have done a live chain read showing the recipient actually received the amount, and that read is a required human step, not a contract check, and the recorded hash lets anyone audit it later. For PAID, the contract books spent plus amount, clears the reservation, clears in_flight, clears transfer_dispatched_at_ns, permanently consumes the nonce, appends the receipt, and moves to PAID. For READY, on a human confirmed failure where the recipient balance shows no such transfer, it releases the reservation, clears in_flight, clears transfer_dispatched_at_ns, and moves to READY, but the first dispatch is marked consumed, so the obligation can never settle again and a genuine retry needs a fresh obligation. The owner must verify on-chain that the transfer failed before resolving READY or CANCELLED. For CANCELLED, it releases the reservation, clears in_flight, clears transfer_dispatched_at_ns, retires the nonce so it cannot be reused, and moves to CANCELLED, which is terminal. This is how every async outcome stays resolvable, and it is never a blind retry of a payment.

## Views

get_policy(policy_id): anyone. Returns the Policy.

get_obligation(obligation_id): anyone. Returns the Obligation.

balances(policy_id): anyone. Returns spent, reserved, limit, funded, and native NEAR headroom as separate figures, never summed.

receipts(start, limit): anyone, paginated. Returns receipts in index order, starting at start, up to limit entries. Pagination is what lets cynex-verify replay from genesis without loading the whole chain at once.

state(): anyone. Returns owner, receipt_index, and last_receipt_hash only. It does not return frozen flags or verifier set size in .

## Timeout constants, frozen

TRANSFER_TIMEOUT_NS equals 600000000000, which is 10 minutes.
EVIDENCE_TIMEOUT_NS equals 3600000000000, which is 1 hour.

These are demo aware by design, not demo shortcuts. The happy path never hits either timeout, so a normal demo runs straight through. A timeout path is demoed with a pre-aged obligation, created an hour or more before the demo, then resolved live in seconds with a real transaction, or with sandbox block time fast forward in tests. Waiting out a timeout live on stage is not the demo plan, and shortening these constants to make that wait bearable would weaken the vault, because a legitimate verifier might not answer in a few minutes and a slow callback could be marked for reconciliation too early.

## Funding path, frozen

Funding is by ft_transfer_call through ft_on_transfer only. The owner, or a funder acting for the owner, calls ft_transfer_call on the configured token, sending tokens to the vault with a msg that must be JSON with a fund_policy field naming an existing policy whose token_id equals the predecessor token contract. ft_on_transfer accepts only the configured token, credits funded for that policy by the transferred amount, and returns 0 unused when the msg and policy are valid. Funding that would take funded past limit is refused in full: the whole amount is returned unused, funded is unchanged, and the rejection is logged with ERR_BUDGET_EXCEEDED. The limit check lives in ft_on_transfer only, not in the shared policy invariant, so freeze and unfreeze still work on an already over-funded policy. If the token is not the policy token, the policy does not exist, or the msg is not valid JSON with a fund_policy field, it returns the full amount as unused, credits nothing, and changes no state. Refunds follow the token contract rule for the returned unused amount.

Plain ft_transfer is explicitly not a funding path and must not be claimed as one. Tokens sent by plain ft_transfer would arrive at the vault account without triggering ft_on_transfer, so they would not be credited to the token ledger, and claiming them as funded would be false. The contract must not treat a plain transfer balance as ledger funds.

Registration, before any settlement: register the vault and each recipient with the token through storage_deposit, one async call each, then confirm with storage_balance_of returning non-null. Registration storage is one time, not per settlement. The agent account also needs gas funding, and the vault needs NEAR for its storage and for 1 yoctoNEAR attached deposits. ft_transfer from the vault attaches 1 yoctoNEAR, as NEP-141 requires.

## Money path, frozen order

Settle validates and reserves synchronously, then dispatches ft_transfer with 1 yoctoNEAR attached and static gas as measured above, chained to on_transfer_complete. The callback books the outcome as described above. Freeze and version bumps block new settle calls only. An in-flight success always finalizes, and is never un-booked because policy changed. A bad agent call never auto-freezes a policy, because that would let the agent brick the demo. Storage exhaustion is a clean rejection with VAULT_STORAGE_EXHAUSTED when native headroom is insufficient for 1 yocto plus gas headroom plus the per-settlement receipt storage reserve, never a panic mid-transfer. The per-settlement reserve covers the new receipt only, and its size is measured in and recorded here.

## cynex-verify, frozen surface

cynex-verify is a frontend deliverable. It replays receipts from genesis through the paginated receipts view, recomputes each prev_hash link, and detects index gaps and hash mismatches. Its CSV columns, frozen here, are: index, prev_hash, obligation_id, recipient, amount, token_id, timestamp, tx_ref, verified_ok.

Acceptance for cynex-verify must include a tampered receipt that it detects, with the tamper output recorded, not only a happy path replay.

frontend builds against this document only. Views consumed: get_policy, get_obligation, balances, receipts with start and limit pagination, and state. Events consumed: NEP-297 receipt events, with the same fields as the stored Receipt. The console must print a live transaction hash and the live chain read that follows it for every action. A console line without either is treated as canned output and fails frontend acceptance.
